# KAIZEN — HTML-бот для Telegram

Самостоятельный продукт на **Telegram Widgets / Bot API 10.4**. Интерфейс находится прямо в сообщении: это HTML с CSS и JavaScript, отправленный методом `sendWidget`. Отдельное окно приложения для сценария не открывается.

Репозиторий: `nesteroviojob-lgtm/codexKaizenhtml`. Старый `codexKaizenbot` и его Vercel-проект не используются. Здесь нужны **новый бот от BotFather, его собственный токен и отдельный проект хостинга**.

## Сценарий

1. `/start` — знакомство с KAIZEN, направления работы, три реальных кейса, пять этапов работы.
2. Кнопка «Обсудить проект» или `/project` — виджет короткого брифа.
3. Кнопками выбираются направление, пожелания по бюджету и срокам. Выбор можно проверить и изменить.
4. После согласия бот присылает сообщение с предложением описать задачу.
5. Клиент отвечает обычным сообщением Telegram. Если нет `@username`, нужно добавить телефон или email в описание.
6. Бот передаёт заявку в настроенный чат команды. Подтверждение клиенту приходит **после успешного ответа Bot API**. Номер вида `HTML-<chat>-<message>` помогает находить заявку и распознавать дубли.

Виджеты пока работают в production только в личном чате с ботом. У них нет клавиатуры и текстовых полей; поэтому описание вводится ответом на сообщение в чате. Виджеты не обращаются к сети и не содержат токенов, внешних шрифтов или библиотек. Отправленные HTML-код и оформление виджета нельзя заменить: после обновления пользователю нужно отправить `/start` или `/project` снова.

## Локальный предпросмотр

Нужен Node.js 24+. Внешних npm-зависимостей нет.

```sh
npm run build
npm start
```

Открыть `http://127.0.0.1:3101`. Это браузерная демонстрация сообщения: можно открыть кейсы, пройти бриф и переключить тему. Она **не отправляет заявки**, не вызывает Telegram API и не содержит токена.

`artifacts/home.html` и `artifacts/brief.html` — настоящий код отправляемых виджетов. `dist/` — только браузерный предпросмотр. Стенд `preview/bridge.js` в отправляемые виджеты не включается.

## Запуск отдельного бота на Vercel

1. В [BotFather](https://t.me/BotFather) создайте **нового** бота командой `/newbot`. Старого бота Mini App не выбирайте.
2. В Vercel создайте новый проект из **`codexKaizenhtml`**. Framework: `Other`, Build Command: `npm run build`, Output Directory: `dist`, Node.js: 24.x.
3. Первый Deploy можно сделать без секретов: откроется только предпросмотр. Сохраните выданный корневой HTTPS-адрес.
4. В Environment Variables нового проекта, окружение Production, добавьте:

| Переменная              | Тип    | Значение                                                    |
| ----------------------- | ------ | ----------------------------------------------------------- |
| `HTML_BOT_TOKEN`        | Secret | Токен **нового** бота от BotFather                          |
| `HTML_BOT_USERNAME`     | Config | Имя нового бота без `@`                                     |
| `HTML_PUBLIC_URL`       | Config | Корневой HTTPS-адрес нового проекта Vercel                  |
| `HTML_WEBHOOK_SECRET`   | Secret | Новый случайный секрет, 32–256 символов `A-Z a-z 0-9 _ -`   |
| `HTML_LEADS_CHAT_ID`    | Config | Числовой ID чата команды для заявок                         |
| `HTML_PRIVACY_OPERATOR` | Config | Реальный оператор заявок: компания или ФИО, до 100 символов |
| `HTML_PRIVACY_CONTACT`  | Config | Контакт для обращений по данным, до 120 символов            |
| `CONFIGURE_HTML_BOT`    | Config | `1`                                                         |

5. Выполните Redeploy. Production-сборка проверит через `getMe`, что токен принадлежит указанному `HTML_BOT_USERNAME`, и установит webhook `/api/telegram` с обновлениями `message` и `widget_query`. Если у бота уже есть другой webhook, настройка остановится до изменения его команд и меню. Preview-сборки не меняют бота.
6. В новом боте отправьте `/start`, затем пройдите заявку и проверьте сообщение в чате команды. Для личного чата получатель предварительно должен нажать Start в **новом** боте; в группе бот должен иметь право отправлять сообщения.

Секреты вводятся только в защищённые настройки Vercel или локальный `.env`, не в HTML, репозиторий или переписку. Main Mini App и Web App URL в BotFather для этого проекта настраивать не требуется.

Если токен или чат ещё не настроены, просмотр работает, но заявка не принимается. `/api/health` показывает наличие конфигурации (`configured`, `leadsConfigured`), а не доказательство live-доставки. Для подтверждения нужен шаг 6.

## Обычный Node.js-сервер

Скопируйте `.env.example` в `.env` и задайте переменные нового бота. Возможны два взаимоисключающих способа получения обновлений:

- Webhook: публичный HTTPS-сервер с `npm start`, затем `npm run setup:bot`.
- Long polling: `npm run bot`. Публичный URL не нужен. Процесс проверяет имя бота, останавливается при уже установленном webhook и не удаляет его.

Нельзя запускать polling параллельно с webhook или вторым polling-процессом.

## Проверки

```sh
npm test
npm run build
# При запущенном npm start, нужны Python Playwright и Chromium:
npm run test:browser
```

Серверные тесты проверяют реальный контракт Widgets API с подменённой доставкой, согласие, доверенный контекст Telegram, обработку неверных/просроченных ответов, контакт без username, экранирование HTML, отказ доставки, частичные повторы, webhook secret и защиту от изменения чужого webhook. Браузерные проверки проходят страницы виджетов на ширинах 200–600 px в светлой и тёмной теме, бриф, ошибку/повтор и честный деморежим. Размер HTML проверяется и при сборке; проверку Python zlib можно выполнить так:

```sh
python3 -c 'import pathlib,zlib; [(print(p.name,len(zlib.compress(p.read_bytes(),9)))) for p in pathlib.Path("artifacts").glob("*.html")]'
```

Браузерный движок отличается от Telegram QuickJS: окончательная проверка рендеринга и живой доставки выполняется в актуальном клиенте Telegram. В этой разработке live-тест без токена нового бота не выполнялся.

## Хранение и повторы

Черновик выбора хранится на устройстве в `localStorage` конкретного сообщения. Описание до финального ответа команде не отправляется. Форма не сохраняет заявки в базе: готовая заявка остаётся в чате команды и в истории Telegram клиента. Контекст брифа восстанавливается из ответа на исходное сообщение бота, действует один час и не требует памяти процесса.

Дедупликация обновлений и лимит пяти заявок за десять минут действуют **в пределах одного процесса**. На нескольких Vercel-инстансах или после перезапуска возможны дубли; при потере сетевого ответа Telegram тоже нельзя гарантировать однократную доставку. Номер заявки стабилен для повторно доставленного update. Перед существенным трафиком нужна общая очередь/БД для дедупликации и rate limit. Никаких автоматических рекламных рассылок нет.

Официальные технические источники: [Telegram Widgets](https://core.telegram.org/bots/widgets), [sendWidget](https://core.telegram.org/bots/api#sendwidget), [WidgetQuery](https://core.telegram.org/bots/api#widgetquery), [answerWidgetQuery](https://core.telegram.org/bots/api#answerwidgetquery).
